# 피드백·설정 저장·로직 테스트 설계

작성일: 2026-11-08

## 1. 의도와 배경

Escaphere는 심심한 사람이 탈출 게임을 찾다가 들어와 몇 분 놀고 나가는 앱이다.
특정 팬층을 겨냥하지 않고, 한 판이 곧 한 세션에 가깝다. 이어하기나 장기 진행은
설계의 중심이 아니다.

이 전제에서 지금 코드의 가장 큰 결함은 **첫 30초에 규칙을 가르치지 못한다는 점**이다.
플레이어가 방향을 눌렀는데 벽에 막히면 `useGameState.move`가 이전 상태를 그대로
반환하고 끝난다. 화면도, 소리도, 진동도 반응하지 않는다. 게임을 처음 만난 사람은
"벽이구나"와 "버튼이 고장났나"를 구분할 수 없다. 몇 분 머무는 사용자에게 이 혼동은
곧 이탈이다.

이 혼동을 없애는 것이 이 작업의 1차 목적이다. 거기에 더해, 피드백 기능을 제대로
만들려면 그것을 켜고 끄는 설정이 앱을 꺼도 유지되어야 하고(심심할 때 켜는 앱은
지하철·침대·대기실에서 소리를 끄고 하는 경우가 많다), 게임 로직의 불변식이 뷰
레이어가 아니라 로직 안에서 지켜져야 한다.

### 현재 상태 (조사 결과)

작업 전 코드베이스에서 확인한 사실들이다. 모두 실제로 검증했다.

- **효과음이 전부 죽어 있다.** `src/hooks/useSfx.ts`의 `SFX_MAP`이 6개 키 모두 `null`
  이라 `playSfx`는 항상 조기 리턴한다. `assets/`에는 아이콘·스플래시 6개뿐이고 사운드
  파일이 없다. `src/constants/sounds.ts`는 존재하지 않는 파일명만 나열한다.
- **BGM도 죽어 있다.** `src/hooks/useBgm.ts`는 사운드를 로드하는 코드가 아예 없어
  `soundRef.current`가 영구 `null`이다. 그런데 홈 화면에는 `BgmToggleButton`이 떠
  있다 — 눌러도 아무 일도 일어나지 않는 버튼이다.
- **이동/벽 피드백 호출부가 죽은 코드다.** `playSfx('move')`와
  `haptic.triggerMove/triggerWall`을 호출하는 곳은 `src/hooks/useGameActions.ts`
  하나인데, 이 훅을 import하는 파일이 0개다. 42줄 전체가 사용되지 않는다.
  `GameScreen`은 `useGameState`를 직접 쓰면서 clear/gameover/hint/undo만 처리한다.
- **설정이 저장되지 않는다.** `src/storage/asyncStorage.ts`에 `saveSettings`/
  `loadSettings`가 구현되어 있지만 **호출하는 곳이 0곳**이다. `SettingsContext`와
  `ThemeContext` 둘 다 순수 `useState`다. 기록(record)과 스트릭은 저장되는데 설정만
  안 되는 비대칭이다.
- **테마 소스가 두 개다.** `AppSettings.theme` 필드는 참조가 0회이고, 실제 테마는
  `ThemeContext.mode`가 따로 들고 있다.
- **`applyUndo`에 횟수 가드가 없다.** `src/logic/undoLogic.ts`의 `pushUndo`는
  `undoRemaining <= 0`을 로직 안에서 막는데, `applyUndo`는 스택 길이만 본다.
  `undoRemaining`이 0인 상태로 호출되면 `-1`로 내려가며 오래된 스냅샷을 pop한다.
  현재는 `GameScreen.handleUndo`와 `GameToolbar`의 `disabled`가 막아주고 있어
  **불변식이 뷰 레이어에만 존재한다.**
- **순수 함수 단위 테스트가 0개이고 테스트 러너도 없다.** `scripts/check-mapgen.js`
  주석이 "No test framework in this project"라고 명시한다. CI는 typecheck →
  check:mapgen → check:layout을 돌리고 전부 통과한다.
- **패키지:** `expo-av@16.0.8`에 의존 중. npm dist-tag가 `sdk-51`에서 멈추고 버전도
  16.0.8에 고정되어 있다 — 다른 expo 패키지가 55.0.x 라인으로 올라간 것과 달리 SDK
  버전 열차에서 내렸다. `expo-audio`에는 55.0.x 라인이 있다(최신 55.0.18).

## 2. 목표

1. **벽 충돌과 이동이 즉시 체감된다.** 방향을 눌러 공이 움직이면 그에 맞는 피드백이,
   벽에 막히면 명확히 다른 피드백이 나온다. 플레이어가 "안 움직인 이유"를 소리/진동
   만으로 알 수 있다.
2. **설정이 실제로 동작하고, 앱을 꺼도 유지된다.** 효과음·진동·색약 모드·테마를
   설정 메뉴에서 바꿀 수 있고, 바꾼 값이 다음 실행에도 남아 있다. 타입에만 존재하고
   아무 일도 하지 않는 설정이 남지 않는다.
3. **게임 로직의 불변식이 로직 안에서 지켜지고, 테스트로 고정된다.** 뷰를 거치지
   않고 로직을 직접 호출해도 안전하다.

### 성공의 모습

- 처음 보드를 받은 사람이 벽에 몇 번 부딪히는 동안 규칙을 스스로 알아낸다.
- 소리를 끄고 앱을 닫았다가 다시 켜면 여전히 꺼져 있다.
- `src/logic/` 아래 순수 함수를 고칠 때 테스트가 회귀를 잡아준다.

## 3. 목표가 아닌 것 (Non-goals)

이번 범위에 들어가지 않는다. 의식적으로 뺀 것이고, 잊어서 뺀 것이 아니다.

- **배경음악(BGM).** 효과음 + 햅틱만 넣기로 결정됐다. `BgmToggleButton`은 BGM 토글이
  아니라 **효과음 토글**로 용도를 바꾼다. `useBgm.ts`는 삭제한다.
- **`animationSpeed` 설정.** 구현이 아예 없고 참조도 0회다. 필드를 **삭제**한다(§6.7).
  애니메이션 속도 조절 자체는 별도 작업이다.
- **모바일 앱 배포.** 안드로이드 전용, 내 폰에 먼저 설치하고 나중에 스토어로 간다는
  방향만 정해졌고, 실제 빌드/배포 작업은 이번 개선 이후로 미뤘다. eas.json, bundle
  identifier, APK 빌드는 이번에 만들지 않는다. 단, **이번 작업의 어떤 선택도 그
  경로를 막지 않아야 한다**(§5 제약 참조).
- **리스폰 시 `moveCount` 리셋.** 검토했고 **현재 동작이 맞다.** 리스폰은 공을 중앙,
  즉 원래 시작 위치로 돌려보내므로 "같은 보드를 처음부터 다시"와 같다. 이동수와
  되돌리기 횟수가 함께 초기화되는 것이 그 의미에 정확히 부합하고, 일시정지 메뉴의
  다시하기(`restart()`)가 이미 똑같이 동작한다. 최고 기록은 "한 번의 시도 중 최선"을
  뜻하며 이것이 의도된 의미다. 변경하지 않는다.
- **도달 불가능한 `'gameover'` 상태 정리.** 타입에 있고 `GameScreen`이 처리하지만 이
  값을 세팅하는 코드가 없다. 없앨지, 실제 패배 조건을 넣을지는 별도 결정 사항이다.
  이번에는 **효과음 키 목록에서만 제외**하고 상태 자체는 손대지 않는다.
- **접근성 라벨.** `accessibilityLabel`/`accessibilityRole`이 전체 0개다. 별도 작업.
- **ESLint 도입.** 별도 작업.

## 4. 실패의 모습 (Anti-goals)

기술적으로 동작해도 이렇게 되면 실패다.

- **피드백이 시끄럽거나 거슬린다.** 몇 분 쓰는 캐주얼 게임에서 매 이동마다 큰 소리나
  센 진동이 나면 끄게 되고, 끄면 1번 목표가 사라진다. 이동 피드백은 가볍고 짧아야
  하며, 벽 충돌은 "실패"가 아니라 "정보"로 느껴져야 한다.
- **첫 화면에 테마가 번쩍인다.** 설정을 저장하면 앱 시작 시 불러오는 시간이 생긴다.
  기본값(dark)으로 한 프레임 그린 뒤 저장된 light로 바뀌면 깜빡임이 보인다.
- **사운드 파일이 없을 때 앱이 깨진다.** 파일은 사용자가 직접 넣고, 아직 없다. 파일이
  없는 상태에서도 앱이 정상 동작하고 햅틱은 작동해야 한다.
- **테스트가 느려서 CI가 무거워진다.** 현재 `check:mapgen`이 5초, 전체 CI가 가볍다.
  이 균형을 깨면 안 된다.
- **의존성이 불어난다.** 지금 devDependencies는 3개(@types/react, playwright,
  typescript)다. 순수 함수 테스트를 위해 큰 프레임워크를 들여오는 것은 과하다.

## 5. 제약

- **Expo SDK 55 / React Native 0.83.2 / React 19.2.** 기존 버전 라인을 유지한다.
- **웹과 안드로이드 양쪽에서 동작해야 한다.** 웹은 이미 GitHub Pages로 배포 중이다.
  중요한 함의: **`expo-haptics`는 웹에서 동작하지 않는다.** 따라서 웹에서는 효과음이
  유일한 피드백 채널이고, 안드로이드에서는 둘 다 쓸 수 있다. 피드백 설계는 어느 한쪽만
  있어도 의미가 통해야 한다.
- **CI 게이트를 깨뜨리지 않는다.** `npx tsc --noEmit`, `npm run check:mapgen`,
  `npm run check:layout` 세 개가 `.github/workflows/deploy.yml`에서 돌고 있고, 실패하면
  배포가 멈춘다. 새 테스트도 같은 자리에 들어가야 한다.
- **`src/constants/version.ts`는 배포 워크플로우가 생성한다.** 손대지 않는다.
- **향후 안드로이드 빌드를 막지 않을 것.** 웹 전용 API(`window`, `localStorage` 등)를
  `Platform.OS` 가드 없이 새로 도입하지 않는다. 저장은 이미 쓰고 있는
  `@react-native-async-storage/async-storage`를 계속 쓴다.

## 6. 결정된 사항

### 6.1 작업 순서

세 갈래를 이 순서로 진행한다. 앞 단계가 뒤 단계에 의미를 주기 때문이다.

1. 이동/벽 피드백 — `expo-audio` 교체, 이동 판정 리팩터, 효과음·햅틱 배선 (§6.2, §6.3)
2. 설정 — 영구 저장, 설정 모달 신규, 필드 정리 (§6.3, §6.6, §6.7)
3. `applyUndo` 가드 + 로직 유닛 테스트 (§6.4, §6.5)

순서는 사용자가 승인했다. 단, **3번의 테스트 러너를 1번보다 먼저 세워도 좋다** —
1번이 로직에 새 상태를 추가하므로(§6.2) 테스트가 먼저 있으면 그 변경을 테스트로
받을 수 있다. 이 판단은 구현자에게 맡긴다.

### 6.2 피드백을 어떻게 전달하는가 (내 결정)

핵심 난점: `GameScreen`이 "이번 이동이 벽에 막혔다"는 사실을 알 방법이 없다.
`useGameState.move`는 `setState` 업데이터 안에서 모든 판정을 하고 아무것도 반환하지
않는다. 업데이터는 비동기이고 React가 두 번 호출할 수도 있어서, 업데이터 안에서
직접 소리를 내는 것은 안전하지 않다(중복 재생).

**결정: 게임 상태가 "직전에 무슨 일이 일어났는지"를 들고, 화면은 그것을 보고 반응한다.**

`GameState`에 직전 이벤트를 담는 필드를 추가한다. 종류(이동했다 / 벽에 막혔다 /
보드 밖으로 나갔다 / 탈출했다 / 되돌렸다 / 힌트를 봤다)와, **단조 증가하는 일련번호**를
함께 담는다. 일련번호가 필요한 이유: 벽에 연속으로 두 번 막히면 종류가 같아서, 번호가
없으면 화면이 두 번째를 새 사건으로 인식하지 못한다.

`GameScreen`은 그 일련번호 하나만 보는 이펙트를 두고, 종류 → (효과음, 햅틱)의 매핑을
적용한다. 이 구조의 이점:

- **판정이 순수 함수 안에 남는다.** "벽에 막혔다"는 판단이 로직의 결과물이 되므로
  §6.4의 유닛 테스트로 직접 검증할 수 있다. 화면을 띄울 필요가 없다.
- **중복 재생이 구조적으로 막힌다.** 업데이터가 몇 번 불리든 번호가 같으면 이펙트는
  한 번만 돈다.
- **피드백 추가가 선언적이 된다.** 새 피드백은 매핑에 한 줄이다.

구현 세부(필드 이름, 이벤트 종류의 정확한 집합, 이펙트를 `GameScreen`에 둘지 훅으로
뺄지)는 구현자에게 맡긴다.

**이동 판정을 `src/logic/`으로 꺼내는 리팩터가 이 범위에 포함된다.** 지금 이동 해석은
전부 `src/hooks/useGameState.ts`의 `setState` 업데이터 안에 있다(`pushUndo` →
`simulateMove` → `out`/`exit`/동일좌표 분기). `node --test`는 React를 import할 수 없고
`scripts/tsconfig.mapgen.json`은 `src/logic/**`만 컴파일하므로, 판정이 훅 안에 남아
있으면 §6.4의 핵심 테스트("벽에 막혔다"가 전달되는지)를 쓸 수 없다. 따라서 이동 해석을
`src/logic/`의 순수 함수(예: `resolveMove(state, direction): GameState`)로 옮기고 훅은
그것을 호출만 한다. 이것은 "`GameState`에 필드 하나 추가"보다 큰 작업이며, 세 갈래 중
가장 위험한 부분이다.

**주의: `simulateMove`의 반환값에 `'blocked'`를 추가하지 말 것.** 더 쉬워 보이는
우회로지만 `scripts/check-mapgen.js`가 `'stop'`/`'exit'`/`'out'` 값과
`samePos(landPos, pos)` 비교에 직접 의존하고, 타입 검사를 받지 않는 plain JS라 기존 CI
게이트가 런타임에 깨진다. "막혔다"의 판정은 `simulateMove` 바깥(위의 `resolveMove`)에서
하되, 기존 `'stop'` 결과와 좌표 비교를 그대로 활용한다.

**죽은 코드 정리:** `src/hooks/useGameActions.ts`는 바로 이 피드백 배선을 하려다 만
흔적이고 아무도 쓰지 않는다. 위 구조로 대체되므로 **삭제한다**.

### 6.3 효과음과 설정

- **패키지:** `expo-av`를 제거하고 `expo-audio`로 교체한다. 설치는
  `npx expo install expo-audio`로 하여 SDK 55에 맞는 버전이 잡히게 한다(55.0.x 라인).
  `expo-av`는 `package.json`에서 지운다.
- **파일:** `assets/sounds/`에 키 이름 그대로 넣는다. 사용자가 직접 준비하며, 포맷은
  `.wav`(16-bit/44.1kHz/모노) 권장, `.mp3`도 가능. 필요한 키는 6개다.

  | 키 | 언제 | 길이 |
  |---|---|---|
  | `move` | 공이 미끄러져 이동할 때 | 80~150ms |
  | `wall` | 벽에 막혀 못 움직일 때 | 50~120ms, `move`와 확실히 다른 음색 |
  | `out` | 공이 보드 밖으로 날아가 리스폰할 때 | 0.3~0.6s |
  | `clear` | 탈출 성공 | 0.8~1.5s |
  | `hint` | 힌트 공개 | ~200ms |
  | `undo` | 되돌리기 | ~200ms |

  `gameover`는 상태가 도달 불가이므로 제외한다(§3). **`out`은 반드시 효과음이 있어야
  한다** — 결과가 가장 큰 사건인데다 `expo-haptics`가 웹에서 동작하지 않으므로, 소리가
  없으면 웹에서 이 사건은 완전히 무음이 된다.
- **파일이 없어도 동작해야 한다.** 아직 파일이 없고, 사용자가 일부만 넣을 수도 있다.
  해당 키의 파일이 없으면 효과음은 조용히 넘어가고 **햅틱은 정상 동작**해야 한다.
  구현은 지금과 같은 **키별 명시적 매핑**을 유지하고, 파일이 없는 키는 `null`로 둔다.
  `.wav`에 대한 모듈 선언이 없으므로 `import`가 아니라 `require()`를 써야
  `tsc --noEmit`를 통과한다.

  명확히 할 것: **파일만 떨어뜨리면 자동으로 붙지 않는다.** Metro가 `require`를 정적으로
  해석하기 때문에, 없는 파일의 `require`가 코드에 남아 있으면 번들이 깨지고, 없으면
  파일을 넣어도 연결되지 않는다. 둘 다는 불가능하다. 무음 placeholder를 커밋하는 대안은
  파일명·확장자를 정확히 맞춰 덮어쓰게 만들어 더 번거롭다. 따라서 **파일이 추가될 때
  키별로 한 줄 연결하는 작업이 필요**하며, 이는 예상된 후속 작업이다.
- **BGM 제거:** `src/hooks/useBgm.ts`를 삭제한다. `BgmToggleButton`은 **효과음 토글**로
  바꾼다(`settings.sfxOn`). 이름·아이콘·라벨도 그에 맞게 바꾼다.
- **`sounds.ts` 갱신:** 현재 존재하지 않는 파일명 6개(`gameover` 포함)를 나열하고 있다.
  위 표의 6개 키(`move`, `wall`, `out`, `clear`, `hint`, `undo`)로 맞춘다 — `gameover`를
  빼고 `out`을 넣는다. `SfxKey` 타입이 여기서 파생되므로 이 파일이 키의 단일 출처다.
- **설정 저장:** `SettingsProvider`가 마운트 시 `loadSettings()`로 불러오고, 변경 시
  `saveSettings()`로 쓴다. 이미 있는 함수를 쓰면 되고 새로 만들 것은 없다.
- **깜빡임 방지(내 결정):** 불러오기가 끝나기 전에는 앱 본문을 그리지 않는다.
  `SettingsProvider`가 hydration 완료 플래그를 들고, 완료 전에는 **기본값(dark)의 배경색
  으로 칠한 빈 화면**을 보여준다. hydration 전에는 저장된 테마를 알 수 없으므로 기본값
  외에 칠할 색이 없다. AsyncStorage 읽기는 수 ms라 체감되지 않으며, 저장된 light 테마가
  dark로 한 프레임 번쩍이는 것보다 낫다.

  **범위 밖:** 웹에서 번들 로드 전 흰 화면이 잠깐 보이는 현상. Expo가 생성하는
  `dist/index.html`에 배경색 지정이 없어서 생기는 것으로, 지금도 그러하며 이 작업과
  무관하다. 고치려면 웹 HTML 셸을 손대야 하고, 테마를 미리 알려면 `localStorage` 동기
  읽기가 필요해 §5의 제약과 충돌한다.
- **테마 단일화(내 결정):** `AppSettings.theme`을 유일한 출처로 삼고 `ThemeContext`는
  그것을 읽어 쓰기만 한다. `ThemeContext`가 자체 `useState`를 들지 않는다.
  `App.tsx`가 이미 `SettingsProvider` > `ThemeProvider` 순서로 감싸고 있어 구조 변경이
  필요 없다. `toggleTheme`은 `updateSettings({ theme })`를 호출한다.
- **저장 실패는 무시한다.** `asyncStorage.ts`의 기존 방식(try/catch 후 무음)을 유지한다.
  설정 저장 실패로 게임이 멈추는 것은 과하다.

  없다. (2) 이 저장소에 이미 선례가 있다 — `scripts/check-mapgen.js`가 "No test
  framework in this project"라고 명시하며 `scripts/tsconfig.mapgen.json`으로 로직만
  컴파일해 plain node로 돌린다. (3) 로컬 Node 22.14, CI Node 22로 `node --test`가
  안정 기능이다. (4) 비목표에 "의존성이 불어나는 것"이 있다.
  기존 컴파일 산출물(`.mapgen-build/`)을 재사용한다.
- **알려진 설정 함정:** `@types/node`는 이미 전이 의존성으로 설치되어 있어 루트
  `tsc`에서는 `node:test` import가 통과한다. 그러나
  `scripts/tsconfig.mapgen.json`은 `"types": []`이므로 테스트 코드를 그 설정으로
  컴파일하려면 손을 봐야 한다. 테스트를 TypeScript로 쓸지 `check-mapgen.js`처럼
  plain JS로 쓸지는 구현자에게 맡긴다.
- **무엇을 테스트하는가:** `src/logic/` 아래 순수 함수. 특히 통합 스크립트가 간접적으로만
  덮고 있는 미묘한 불변식들:
  - `simulateMove`의 **"현재 칸 벽 검사 → 경계 검사" 순서**. 이 순서가 뒤집히면 보드
    가장자리에서 벽에 막혀야 할 이동이 보드 밖으로 나간 것(`'out'`)으로 오판된다.
    이미 고친 적 있는 버그이고 주석으로 이유가 적혀 있지만 테스트가 없다.
  - `applyUndo` / `pushUndo`의 횟수 가드와 스택 동작 (§6.5).
  - `findShortestSolution`이 해가 없는 보드에서 `null`을 반환하는 것.
  - §6.2에서 추가되는 이벤트 판정 — 특히 **벽에 막힌 이동이 상태를 바꾸지 않으면서도
    "막혔다"는 사실은 전달하는지**.
- **CI 배선:** `package.json`에 스크립트를 추가하고 `deploy.yml`의 "Verify map
  generator" 단계 근처에 넣는다. 기존 세 게이트와 같은 성격이다.
- **TDD:** `applyUndo` 가드는 실패하는 테스트를 먼저 쓰고 고친다. 결함과 수정이 모두
  명확해서 테스트를 먼저 쓰는 비용이 거의 없다.

### 6.5 `applyUndo` 가드

`applyUndo`가 `undoRemaining <= 0`일 때 상태를 그대로 반환한다. `pushUndo`와 대칭이
된다. `GameScreen.handleUndo`와 `GameToolbar`의 `disabled`는 UX를 위해 그대로 둔다 —
비활성 버튼은 여전히 비활성으로 보여야 한다. 차이는 **로직이 더 이상 뷰의 가드에
의존하지 않는다는 것**이다.

### 6.6 설정 메뉴

**설정 모달을 새 컴포넌트로 만든다.** 사용자가 설정 메뉴의 고도화를 요청했고, 토글을
`PauseMenu`에 밀어넣으면 행동(계속하기/다시하기/홈으로)과 설정이 한 모달에 섞여 6줄이
되기 때문이다. 행동과 설정은 분리한다.

**열리는 곳 두 군데:**

- 홈 화면 상단바의 ⚙ 버튼
- `PauseMenu`의 "설정" 버튼 — 게임 중에 바꿀 수 있어야 한다는 요구를 충족한다

하나의 컴포넌트를 두 곳에서 연다. `PauseMenu`에는 버튼 한 개만 늘어나므로 모달이
크게 높아지지 않는다.

**설정 모달에 들어가는 토글 4개:**

| 토글 | 필드 | 현재 상태 |
|---|---|---|
| 효과음 | `sfxOn` | 바꿀 UI가 없었다 |
| 진동(햅틱) | `hapticOn` | 바꿀 UI가 없었다. 안드로이드 전용 — 웹에서는 숨기거나 비활성 |
| 색약 모드 | `colorBlindMode` | **구현은 완성, 켤 방법이 없었다** |
| 테마 | `theme` | `ThemeContext`의 별도 상태였다(§6.3에서 단일화) |

네 개는 모두 별개 설정이다. 하나로 묶지 않는다.

**색약 모드를 넣는 이유:** 이미 동작하는 기능이다. 켜면 탈출구에 ★를 그리고
(`ExitTile`), 힌트 경로에 점선 테두리를 넣는다(`HintPathOverlay`). 색만으로 구분하기
어려운 사용자를 위한 기능이 완성되어 있는데 도달할 수 없는 상태였다. 설정 자리를
만드는 중이므로 추가 비용이 거의 없다.

**홈 상단바는 유지:** ♪(효과음)와 테마 버튼은 빠른 접근용으로 남긴다. 설정 모달과
같은 값을 가리키므로 한쪽에서 바꾸면 다른 쪽에도 반영된다.

### 6.7 `AppSettings` 필드 정리

현재 6개 필드 중 4개가 유령이다 — 코드가 읽지 않거나, 읽어도 효과가 없거나, 바꿀
UI가 없다. 이 작업의 요점이 유령 설정을 없애는 것이므로 필드 자체를 정리한다.

**삭제:**

- `bgmOn` — BGM이 범위에 없고 `useBgm`도 삭제된다. 그 버튼은 효과음 토글로 용도가
  바뀐다. 남겨두면 같은 혼동을 다시 만든다.
- `animationSpeed` — 참조 0회, 구현 없음.

**남기고 전부 배선 + 저장:** `sfxOn`, `hapticOn`, `colorBlindMode`, `theme`.

결과적으로 **네 필드 모두 코드가 실제로 쓰고, 바꿀 UI가 있고, 저장된다.** 지금처럼
"타입에는 있는데 아무 일도 하지 않는 설정"이 남지 않는다.

저장 데이터 호환은 문제되지 않는다 — 설정 저장 자체가 이번에 처음 생기므로 기존
저장 데이터가 없다.

## 7. 구현자에게 맡기는 것

- §6.2 이벤트 필드의 이름, 이벤트 종류의 정확한 집합, 이펙트 배치 위치.
- 효과음과 햅틱의 구체적 조합 — 어떤 이벤트에 어느 햅틱 강도를 쓸지. `useHaptic`에
  이미 `triggerMove`(Light) / `triggerWall`(Medium + Warning) / `triggerClear`
  (Success) / `triggerGameover`(Heavy ×2)가 있다. 반목표("시끄럽거나 거슬린다")를
  기준으로 판단하되, **이동은 가볍게, 벽은 그와 구별되게**를 지킨다. `out`에는 햅틱이
  아직 배정되지 않았다 — 쓰이지 않는 `triggerGameover`(Heavy ×2)가 자연스러운 후보이고,
  이름을 바꿀지는 구현자가 정한다.
- 설정 모달의 생김새 — 토글 위젯의 형태(스위치 대 아이콘 버튼), 라벨 문구, 모달 대
  풀스크린. 기존 `PauseMenu`·`ClearModal`의 모달 스타일과 `IconButton`을 참고해 앱의
  나머지와 어긋나지 않게 한다. 웹에서 진동 토글을 숨길지 비활성으로 보일지도 포함.
- 테스트 파일 위치와 분할, 컴파일 산출물 재사용 방식(기존 tsconfig 확장 대 신규 설정).
- 커밋 분할. 세 갈래가 독립적이므로 따로 나누는 것이 자연스럽다.

## 8. 검증

작업이 끝났다고 말하기 전에 통과해야 하는 것들이다.

- `npx tsc --noEmit` 통과.
- `npm run check:mapgen` 통과 (기존 불변식이 그대로 성립). `simulateMove`를 건드렸다면
  특히 중요하다 — 이 스크립트는 타입 검사를 받지 않으므로 런타임에만 깨진다.
- `npm run check:layout` 통과. 주의: 이 스크립트는 게임 화면만 측정하고 홈 화면은
  텍스트로 클릭해 지나갈 뿐이다. 따라서 **홈 상단바·`PauseMenu`·설정 모달 변경은 이
  검사가 잡아주지 않으므로 직접 확인해야 한다** — 특히 토글 4개가 든 설정 모달이
  360x640에서 화면을 넘지 않는지.
- 새 로직 테스트 전부 통과. `applyUndo` 가드 테스트는 **수정 전에 실패하는 것을 먼저
  확인**한다.
- 실제 앱에서 확인:
  - 벽에 막힐 때 피드백이 오고 이동과 구별된다.
  - 설정 모달이 홈의 ⚙ 버튼과 일시정지 메뉴의 설정 버튼 양쪽에서 열린다.
  - 토글 4개가 각각 동작한다. 효과음을 끄면 소리가 멈추고, 진동을 끄면 진동이
    멈추고, 색약 모드를 켜면 탈출구에 ★가 뜨고, 테마가 바뀐다.
  - 각 토글을 끄고 앱을 재시작하면 모두 그대로 유지된다.
  - 홈 상단바의 ♪·테마 버튼과 설정 모달이 같은 값을 가리킨다 — 한쪽에서 바꾸면
    다른 쪽에도 반영된다.
  - 테마를 바꾸고 재시작하면 유지되며, **저장된 테마가 기본값(dark)으로 한 프레임
    그려지지 않는다**. (웹에서 번들 로드 전 흰 화면은 범위 밖 — §6.3.)
  - 사운드 파일이 없는 상태에서도 앱이 정상 동작하고 햅틱은 작동한다.
  - 일시정지 메뉴에서 설정을 바꾸고 게임으로 돌아가면 바로 적용되어 있다.
